1. ERROR TYPE
   - TimeoutError → the element or page state was never reached (not found, not visible, or page didn't load)
   - AssertionError → the page loaded but the value was wrong or missing
   - Other → note the exception class

   ASSERTION CLOSE-MATCH RULE: If the error shows Expected: "X" but Actual contains a
   near-variant of X (e.g. "Deal Group" vs "Deal Groups", minor wording, plural/singular,
   capitalisation, or the expected string appears as a substring of an actual item), the
   test assertion is simply out of date → Script Issue (category c/e). Do NOT classify
   as Functional Issue just because the exact string changed — these are test data mismatches,
   not app regressions. Only escalate to Functional Issue if the expected concept is
   entirely absent from the actual output with no recognisable variant.

   SAME-RUN RELIABILITY (check this first for Background/setup failures — weight by
   the stated ratio, it is NOT a binary signal):
   If the Failure Facts include a "Same-Run Reliability" note, it reports how many of
   THIS feature's other Background executions succeeded in this same run (each scenario
   gets its own independent Background run):
   - "PASSED for X/Y (≥50%)" → the setup demonstrably works most of the time this run.
     Classify as Script Issue (category c), an intermittent timing/wait race — recommend
     adding/increasing an explicit wait. Do NOT classify as Functional, regardless of the
     timeout or DOM evidence.
   - "only PASSED X/Y (<50%)" → this is a FREQUENTLY reproducing failure, not a rare
     blip — most executions this run failed the same way. Do NOT default to "just add a
     wait". Weigh it like any other repeated failure: check DOM/screenshot/network
     evidence normally, and lean toward flagging it for investigation (category a/b or a
     script fix that addresses a real, consistently-triggered problem) rather than

   - "FAILED for all N execution(s)" → no same-run evidence either way; fall through to
     the other signals (DOM, screenshot, history) to decide the category as usual.

3. VISUAL + DOM EVIDENCE (screenshot, page DOM text, UI check)
   Check in this order — each overrides the one below it:

   A. SCREENSHOT (highest authority — look at this first if provided)
      - If the screenshot shows the text/element the test was looking for → Script Issue.
        The element exists; the locator or timing is the problem. Do not classify as
        Functional Issue regardless of DOM text or UI Check result.
      - If the screenshot shows the page fully loaded with no trace of the expected
        element → evidence the element was genuinely absent; lean Functional/Data Issue.
      - POST-ACTION STATE MISMATCH: If the screenshot shows UI state that contradicts
        what a successful prior action should have produced — modal still open after OK
        click, spinner still active after save, form unchanged after submit — the action
        did not have its expected effect on the app. Classify as Functional Issue
        regardless of what the next locator targets. Do NOT classify as Script Issue.

   B. PAGE DOM TEXT (provided as a text block — scan it directly)
      - The text is a raw extraction of visible DOM content at failure time.
      - If the expected text IS present (even as part of a longer word, e.g. "Deal Group"
        inside "Deal Groups") → the element exists, locator is stale → Script Issue.
      - If the expected text is absent → element did not exist at that moment; may be
        Functional or data issue — cross-check with action timeline and history.

   C. UI CHECK row (programmatic substring match — treat as a hint, not proof)

      - "NOT found" is more reliable — if the term is absent from the full DOM, the
        element almost certainly was not on the page.

   D. CONFIRMED-SAVE PATTERN
      - If a success toast ("Successfully created", "saved successfully") appeared as the
        last PASSED action immediately before the timed-out locator, the backend persisted
        the change. A timeout on the very next check = stale locator → Script Issue.

4. PLAYWRIGHT CALL LOG (if present)
   The call log shows which element(s) the locator resolved to during polling.
   Any of the following patterns = stale locator → Script Issue:
   - Resolved to a DIFFERENT element than the one the step was acting on
   - Resolved to element A, then switched to element B (phase shift) — the XPath is
     too broad; after A changed state, B started matching unintentionally
   - `waitForLocatorHidden` never resolved because a residual element kept matching
     (locator matches more elements than intended — fix the XPath, not the app)

5. HISTORY

   - "regression" (passed recently, now failing) = a change landed after it last passed;

   - "first recorded occurrence" (no prior history) = could be a new app change or a new script gap
